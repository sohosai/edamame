# Edamame

この文書では、Edamame の全体設計、配信の仕組み、データモデル、および各コンポーネントの責務を説明する。

Edamame は、ライブ HLS 配信を担うインメモリ配信システムである。
一般的なファイルベースの HLS 配信では、エンコーダがプレイリスト（`.m3u8`）とセグメントファイル（`.ts`）の両方をオリジンサーバに書き出す。
これに対し、Edamame では「プレイリストの生成と配信状態の管理（`controller`）」と「セグメントファイルのキャッシュとクライアントへの配信（`worker`）」を別々のプロセスに分けている。

配信は次の 5 段階で進む。

1. `publisher` が映像を MPEG-TS（`.ts`）のセグメントファイルに切り出し、`controller` に `PUT` する。プレイリストは送らない。
2. `controller` が受け取ったセグメントファイルに `0` 始まりの連番（`sequence`）を割り当て、原本（正規データ）としてメモリ上に保管する。
3. `worker` が一定間隔で `controller` と同期（`sync`）し、不足しているセグメントファイルを `controller` から取得してメモリ上にキャッシュする。
4. `client`（HLS プレイヤー）が `controller` からプレイリスト（`.m3u8`）を取得する。`controller` は、公開対象のセグメントをキャッシュしている稼働中の `worker` を選び、その `worker` の公開 URL を書き込んだプレイリストをリクエストごとに生成して返す。
5. `client` は、プレイリストに書かれた `worker` からセグメントファイル（`.ts`）を取得して再生する。

```text
publisher ─── (1) PUT セグメント ──────────────────────> controller
worker    ─── (3) PUT 登録 / POST sync / GET セグメント ─> controller
client    ─── (4) GET プレイリスト (.m3u8) ────────────> controller
client    ─── (5) GET セグメント (.ts) ────────────────> worker
```

Edamame が対象とするライブ配信とは、セグメントファイルが継続的に追加され、プレイリストの表示範囲（スライディングウィンドウ）が更新され続ける配信を指す。
オンデマンド配信（VOD）には対応しない。

## 各コンポーネントの役割

`controller` は台数によらず同じ cluster の選出処理を使い、生存している中で最大の metric の機体を leader にする。
seed がない場合も後から peer が参加できる。
以下の保存、採番、プレイリスト生成は leader が担当し、follower はリクエストを転送する。

**controller** は、`publisher` から受け取ったセグメントファイルを検証し、セグメント識別子にセグメント番号（`sequence`）を割り当ててメモリ上に正規データとして保存する。
保存容量は `--storage-capacity` で指定し、合計バイト数が上限を超えたときは書き込んだ順に古いセグメントファイルから削除する。
また、`worker` の登録と `sync` を受け付け、各 `worker` のキャッシュ状況に基づいて画質（`quality`）ごとに公開範囲を決める。
`client` からプレイリストのリクエストを受けたときは、タイムアウトしていない `worker` の中から `quality` ごとに重み付きで配信先を選び、プレイリストを生成して返す。
`publisher` が外部配信のマスタープレイリスト URL を登録している場合は、公開の遅れに応じた割合で `client` を外部配信へリダイレクトする。

**worker** は、起動時に `controller` に自身を登録し、登録レスポンスで指示された間隔（`sync_interval_ms`）で `sync` を送る。
`sync` レスポンスの `fetch_segments` に従って `controller` からセグメントファイルを取得し、メモリ上にキャッシュする。
キャッシュしているセグメントファイルを `client` に配信し、`(channel_id, quality)` ごとのキャッシュ上限（`--cache-limit`）を超えた古いセグメントファイルを削除する。
`worker` は、配信全体の配置判断やプレイリストの生成を行わない。

**publisher** は、セグメントごとにセグメント識別子（`identifier`）を付けて `controller` に `PUT` する。
このとき、クエリパラメータでセグメント長（`duration_ms`）とビットレート（`bandwidth`）を指定する。
複数の画質（`quality`）を配信する場合、同じ時間帯のセグメントには画質が違っても同じセグメント識別子を使う。
セグメントを暗号化する場合は、あらかじめ AES-128-CBC で暗号化したセグメントファイルを `PUT` し、暗号鍵の URI（`key_uri`）と初期化ベクトル（`iv`）を指定する。
暗号鍵そのものの配布は `publisher` 側または外部の鍵配信サーバが担い、プレイリストは `PUT` しない。

**client** は、`controller` からマスタープレイリストとメディアプレイリストを取得し、メディアプレイリストに記載された `worker` の URL からセグメントファイルを取得して再生する。

## 配信の仕組み

### 1. セグメントの登録と連番の採番

`channel_id` と `quality` を事前に作成する専用の API はなく、最初のセグメントファイルを `PUT` したときに自動的に作られる。
`publisher` が番号ではなく文字列のセグメント識別子（`identifier`）を付けて `PUT` するのは、複数の `quality` の間で同じ時間帯のセグメント番号をそろえるためである。

`controller` は新しいセグメント識別子を受け取るたびに、`channel` ごとの連番（`sequence`）を `0` から順に割り当てて 1 対 1 に対応付ける。
別の `quality` から同じセグメント識別子で `PUT` された場合は、すでに割り当て済みの同じセグメント番号を使う。
識別子とセグメント番号の対応は、その識別子を持つセグメントファイルがいずれかの `quality` に保存されている間だけメモリ上に保持する。
同じ識別子を後から別の `quality` に `PUT` すると、すでに決まっている古いセグメント番号で保存されるため、その `quality` の最新セグメント番号は変わらない。

同じ `channel` のすべてのセグメントは、同じ `duration_ms` でなければならない。
`controller` はその `channel` で最初に成功した `PUT` の `duration_ms` を秒に直し、小数点以下を切り上げた整数（下限は 1 秒）をセグメント長の基準値として固定する。
HLS のライブ配信では `#EXT-X-TARGETDURATION` を途中で変更できないため、`channel` が存在する間はこの基準値を変えない。

セグメントを暗号化する場合、`publisher` は `PUT` 時に `key_uri`（および任意の `iv`）を指定する。
暗号鍵の実体は `publisher` 側が配信し、`controller` と `worker` は鍵を保存も配信もしない。
`controller` はセグメント番号ごとに `key_uri` と `iv` を記録し、メディアプレイリストの生成時に暗号化セグメントの直前へ `#EXT-X-KEY` を出力する。
暗号鍵の URI や IV はセグメントごとに変更でき、暗号化なしのセグメントに戻る箇所では `#EXT-X-KEY:METHOD=NONE` を出力する。
`iv` を省略したセグメントでは、再生側が HLS 仕様（RFC 8216）に従ってメディアシーケンス番号を IV として使う。

### 2. worker の同期と公開範囲の決定

`controller` にセグメントを `PUT` した直後は、`worker` がまだその複製を取得していないため、すぐにはプレイリストへ載せない。
もし `worker` がキャッシュしていない段階でプレイリストに載せてしまうと、`client` が `worker` にアクセスしたときに `404 Not Found` になるからである。

そこで `controller` は、次の 3 つの段階でプレイリストに載せる範囲（公開範囲）を決める。

1. **直近のセグメントの範囲（キャッシュ対象）** ：`quality` ごとに、保存されている最大のセグメント番号を最新とする。最新から `--playlist-segments`（6 以上）個分さかのぼった範囲を、`worker` がキャッシュする対象にする。範囲の先頭が 0 より小さくなる場合は 0 から数える。
2. **公開待ち** ：最初の未公開セグメントを `PUT` してから、`--publish-wait-ms` で指定した時間が過ぎるまでを公開待ちとする。この間に後続の `PUT` が来ても、待ち時間の終了時刻は延ばさない。公開待ちの間は、未公開セグメントを公開範囲にも、古い範囲へ戻すときの候補にも含めない。公開待ちが終わった時点で存在するセグメントは、公開可能として扱う。
3. **公開範囲の決定** ：`quality` ごとに、`--sync-timeout-ms` 以内に `sync` を送っている `worker` を候補にする。候補の `worker` が公開可能なセグメントを途切れずにキャッシュしている範囲のうち、最新のものを最大 `--playlist-segments` 個まで公開範囲として採用する（`worker` が保持している連続範囲が短い場合は、その短い範囲を公開することがある）。

公開範囲は `quality` ごとに独立して決まり、`quality` 間で範囲を一致させる必要はない。
公開範囲の更新は `worker` から `sync` を受けた時にだけ行い、プレイリストの `GET` リクエスト時には変更しない。
現在の公開範囲を保持している稼働中の `worker` が 1 台でもいれば、より新しい候補ができるまで現在の範囲を維持する。
現在の公開範囲を保持している `worker` がいなくなった場合は、次の `sync` で、より古い範囲も候補に含めて配信できる最新の連続範囲へ切り替える。
切り替えが終わるまでのプレイリストリクエストには、`503 Service Unavailable` を返すことがある。
また、公開範囲のセグメントファイルが容量超過などで `controller` のメモリから欠落している場合、`controller` はその `quality` のメディアプレイリストを作らず `422 Unprocessable Entity` を返す。

`publisher` が新しいセグメントを送らなくなって、最後の `PUT` から `duration_ms × --playlist-segments + --publish-wait-ms` を超えると、その `quality` は停止中とみなす。
停止中の `quality` はマスタープレイリストから除外し、メディアプレイリストは `503 Service Unavailable` を返す。
停止中も保存済みのセグメントと `worker` のキャッシュは削除しない。
停止後に再開した場合は、停止前のセグメント番号を公開範囲とキャッシュ対象から除き、再開後の新しいセグメントだけを公開する。

### 3. プレイリスト生成と配信先の振り分け

`controller` は、`sync` が `--sync-timeout-ms` 以内に届いている `worker` だけを配信先の候補にする。
再登録によって設定を更新した `worker` については、それまでに報告されていたキャッシュ一覧を無効にする。

メディアプレイリストのリクエストを受けると、`controller` は `quality` ごとに配信先の `worker` を 1 台選ぶ。
その `quality` の公開範囲をすべてキャッシュしている `worker` が複数いれば、登録された重み（`weight`）の比に従って選び、重みが同じなら順番に選ぶ。
重みを変更したときや候補の `worker` が増減したときは、その時点から重みの比に従って選び直す。
`quality` が違えば別の `worker` を選んでもよく、公開範囲または配信先の `worker` がない `quality` のメディアプレイリストリクエストには `503 Service Unavailable` を返す。

また、`channel` には外部配信のマスタープレイリスト URL を 1 つ登録できる（`PUT /channels/{channel_id}/external`）。
登録されている場合、`controller` は `master.m3u8` のリクエストに対して公開の遅れに応じた割合で `302 Found` を返し、`client` を外部配信へ振り分ける。
外部配信のセグメントファイルは Edamame の正規データではないため、`client` が外部配信から直接取得し、`controller` と `worker` は取得も保存もしない。

## データモデルと不変条件

### 識別子とセグメント属性

セグメントは、`channel_id`、`quality`、`sequence`（セグメント番号）の 3 つの組み合わせで区別し、1 つのセグメントを 1 つの MPEG-TS ファイル（`.ts`）として保存する。

- `channel_id`、`quality`、`worker_id`、およびセグメント識別子（`identifier`）には、半角英数字、`_`、`-`（`[A-Za-z0-9_-]`）を 1 文字以上 64 文字以下で使える。`quality` に `master` は使えない。
- `sequence` は HLS 仕様のメディアシーケンス番号（media sequence number）であり、先頭に不要な `0` を付けない 10 進数の `u64` で表す。セグメント取得時のファイル名は `{sequence}.ts` だけを許可する。
- `duration_ms`：セグメントの長さをミリ秒で表す 500 以上の整数。`PUT` のたびに必須であり、同じ `channel` 内で固定される。
- `bandwidth`：`quality` のビットレートを bit/s で表す正の整数。`PUT` のたびに必須であり、同じ `quality` 内で固定される。
- `resolution`：`quality` の解像度を `{width}x{height}` で表す任意の属性。一度指定した後は同じ `quality` 内で固定される。
- `key_uri`：セグメントの復号に使う AES-128 暗号鍵の `http` または `https` 絶対 URL（任意）。`key_uri` を付けないセグメントは暗号化なしとして扱う。
- `iv`：`key_uri` と組で指定する 16 バイト（16 進数 32 文字）の初期化ベクトル（任意）。

### 不変条件

- `controller` が持つセグメントファイルが正規データであり、`worker` のセグメントファイルは再取得できる複製である。
- 同じ `channel`、`quality`、セグメント番号のセグメントは 1 つだけ存在する。
- 保存されている同じ識別子で同じバイト列を再 `PUT` すると `200 OK` を返し、同じ識別子で異なるバイト列を `PUT` すると `409 Conflict` を返す。
- セグメントファイル、セグメント識別子とセグメント番号の対応、および暗号化の指定は `controller` のメモリ上だけに保持し、再起動で失われる。`controller` は起動するたびにセグメント番号を `0` から振り直す。冗長化した構成でも状態は複製せず、leader の交代で同じ状態消失と採番のリセットが起きる。
- `controller` はメモリ上の合計サイズが `--storage-capacity` を超えないよう、書き込んだ順に古いセグメントファイルから削除する。セグメントファイルを削除したときは、そのセグメント番号の暗号化の指定と識別子の対応も削除する。
- 容量超過で削除された `quality` に同じ識別子を再 `PUT` したとき、別の `quality` に同じ識別子が残っていれば、以前と同じセグメント番号に保存し直す。このとき、古いバイト列をキャッシュしているか取得中の `worker` には、次の `sync` で再取得を指示する。
- `worker` はセグメントファイルをメモリ上にキャッシュし、`(channel_id, quality)` ごとに `--cache-limit` を超えた古いものから削除する。
- プレイリストはリクエストのたびに現在の公開範囲から生成し、生成済みのプレイリストは保存しない。
- 配信できるセグメントファイルは MPEG-TS（`.ts`）だけである。

## 用語一覧

| 用語 | 説明 |
| --- | --- |
| publisher | セグメントファイルを作成し、`controller` に `PUT` する送信側ソフトウェア |
| client | HLS のプレイリストを `controller` から、セグメントファイルを `worker` から取得して再生する HLS プレイヤー |
| ライブ配信 | セグメントファイルが継続的に追加され、プレイリストが更新され続ける配信 |
| controller | 正規データの保管、セグメント番号の採番、プレイリストの生成、`worker` の管理と選択を担当するサーバ |
| leader | 生存している controller の中で優先度が最大であり、状態の保存と業務 API の処理を担当する |
| follower | 状態を持たず、読み取りと sync を leader へ redirect し、認証付き PUT を中継する |
| worker | `controller` からセグメントファイルを取得してメモリにキャッシュし、`client` に配信するサーバ |
| 正規データ | `controller` がメモリ上に保持する元のセグメントファイル。`worker` が持つキャッシュは、失われても `controller` から再取得できる複製である |
| channel | `channel_id` で識別する 1 本の配信ストリームの単位 |
| quality | `quality` で識別する `channel` 内の画質（ビットレートや解像度）の単位（例：`1080p`、`720p`） |
| セグメント | `channel` と `quality` に属する一定時間ごとの映像や音声の断片（HLS の Media Segment） |
| セグメントファイル | 1 つのセグメントを格納した MPEG-TS（`.ts`）ファイル |
| セグメント識別子 | `publisher` がセグメントを `PUT` するときに付ける名前（`identifier`）。画質が違っても、同じ時間帯のセグメントには同じ識別子を付ける |
| セグメント番号 | `controller` がセグメント識別子に対して `channel` ごとに 0 から順に割り当てる連番（`sequence`、HLS のメディアシーケンス番号） |
| 暗号鍵の URI | セグメントの復号に使う AES-128 暗号鍵の取得先 URL（`key_uri`）。セグメントごとに `PUT` で指定する |
| IV | AES-128-CBC でセグメントを復号するときの 16 バイトの初期化ベクトル。セグメントごとに `PUT` で 32 文字の 16 進数として指定する |
| sync | `worker` が一定間隔で `controller` にキャッシュ状況と取得中セグメントを報告し、不足分の取得指示を受け取る同期処理 |
| キャッシュ一覧 | `worker` が現在キャッシュしているセグメントの一覧。`sync` リクエストの `cached_segments` で送る |
| 直近のセグメントの範囲 | 各 `quality` の最新セグメント番号から `--playlist-segments` 個分さかのぼった番号の範囲 |
| キャッシュ対象 | `worker` がメモリにそろえておくべきセグメントファイル。すべての `channel` と `quality` の「直近のセグメントの範囲」が対象になる |
| 未キャッシュ | キャッシュ対象のうち、`worker` のキャッシュ一覧にまだないセグメント。`sync` レスポンスの `fetch_segments` で取得を指示する |
| 公開待ち | 新しいセグメントが `PUT` されてから、プレイリストの候補にするまで待つ時間（`--publish-wait-ms`）。この間に `worker` がセグメントを取得する |
| 公開可能 | 公開待ちが終わり、プレイリストに載せる対象になり得るセグメント |
| 公開範囲 | プレイリストに実際に載せる連続したセグメント番号の範囲。公開可能なセグメントのうち、稼働中の `worker` が途切れずにキャッシュしている範囲から `quality` ごとに決める |
| 保存容量 | `controller` がメモリ上に保存するセグメントファイルの合計バイト数の上限（`--storage-capacity`） |
| キャッシュ上限 | `worker` が `(channel_id, quality)` ごとにキャッシュするセグメントファイル数の上限（`--cache-limit`） |
| 重み | 複数 `worker` 間で配信先を選ぶ比率を決める 1 以上の整数（`--weight`）。`worker` が登録時に宣言する |
| 外部配信 | Edamame とは別のオリジンや CDN で配信している同じ番組の HLS ストリーム。`master.m3u8` から `302 Found` で `client` を転送し、負荷や障害を分散する |
| マスタープレイリスト | `channel` 内の利用可能な `quality` ごとのメディアプレイリストを列挙したプレイリスト（`master.m3u8`） |
| メディアプレイリスト | 1 つの `quality` の公開範囲に含まれるセグメントファイル URL を列挙したプレイリスト（`{quality}.m3u8`） |

## 非目標

- worker の負荷に応じた動的な配置
- fMP4、LL-HLS、バイト範囲、複数音声
- 暗号鍵の保管と配信
- AES-128 以外の暗号化方式
- controller のセグメントファイルとメタデータの永続化
- worker のキャッシュの永続化
- メトリクス用のエンドポイント
- controller 単体での TLS 終端（worker は単体での TLS 終端および ACME に対応する）
- 全 quality の公開範囲を一致させること
