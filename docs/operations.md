# 運用

起動と各オプションは [controller](./controller.md)、[worker](./worker.md)、[publisher](./publisher.md) を参照する。
この文書には、コンポーネント間の調整、ネットワークの前提、全体の確認、障害の切り分けをまとめる。
複数 controller の構成と選出規則は [冗長化](./cluster.md)、監視は [可観測性](./observability.md) を参照する。

## パラメータ設計とメモリ見積もり

### 同期と公開待ち

セグメントを保存しても、worker が取得して次の sync で報告するまでは配信先として使えない。
次の値をセグメント長とネットワーク速度に合わせて調整する。

| 項目 | 目安 |
| --- | --- |
| controller の `--sync-interval-ms` | セグメント長より十分短くする。6 秒セグメントなら `1000` ミリ秒など |
| controller の `--sync-timeout-ms` | 一時的な同期遅延で候補から外れないよう、同期間隔の 3 倍以上を推奨する。例：`10000` ミリ秒 |
| controller の `--publish-wait-ms` | 取得指示と完了報告の 2 回の sync を見込み、同期間隔の 2 倍を出発点にする。例：`2000` ミリ秒 |
| worker の `--cache-limit` | `--playlist-segments` より 1 以上大きくすることを推奨する。公開中と次の範囲を同時に保持するため、6 に対して 12 など |

これらは公開を保証する条件ではない。
worker は 1 バッチ内のセグメントを直列で取得するため、全 channel / quality の取得時間と、同期処理自体の時間も必要になる。
公開の遅延が続く場合は、待ち時間だけを増やす前に取得の速度と失敗を確認する。
公開範囲の規則は [controller](./controller.md#公開範囲の決定)、取得の動作は [worker](./worker.md) を参照する。

### worker の重み

同じ性能なら同じ重みを使い、配信に使える帯域に合わせて相対値を決める。
重み `4` と `1` なら、候補が変わらない間のメディアプレイリストの選択回数は 4 対 1 になる。
視聴者の接続時間や各画質のサイズは異なるため、通信量そのものが同じ比率になる保証はない。
重みは自動調整されず、一時的に負荷が高くなっても候補として選ばれ続ける。

### メモリ容量

controller の `--storage-capacity` はセグメント本体の保存量、worker の `--cache-limit` はファイル数を制限する。
メタデータ、受信中や取得中の body、送信中の参照、TLS バッファなどを含むプロセス全体の上限ではない。
OS やコンテナへ割り当てるメモリには余裕を持たせる。

同じ時間帯の全 quality の最大セグメントサイズの合計を 1 セットとして見積もる。
channel ごとにサイズが違う場合は、以下の値を各 channel で計算して足し合わせる。

- controller：保持したいセット数 × 1 セットの最大サイズ
- worker：`--cache-limit` × 1 セットの最大サイズ

controller の保持数は、公開範囲に公開待ちと取得遅延の分を加えた数より大きくする。
原本が消えても worker にキャッシュが残る場合はあるが、原本が欠落した公開範囲のプレイリストは `422` になる。

例として、6 秒セグメント、1080p 12 Mbps、720p 6.5 Mbps、480p 1.4 Mbps の合計は 1 セットあたり約 14.2 MiB になる。
10 セットを 3 channel で保持すると controller のセグメント本体は約 426 MiB となり、`512MiB` は本体を保持する容量の目安になる。
worker が `--cache-limit 12` で同じ 3 channel を持つと、本体だけで約 512 MiB になる。
実際には VBR の最大サイズとメタデータなどを考慮し、平均ビットレートの計算だけで上限を決めない。

## 通信の保護と公開範囲

公開する経路を次のように分ける。

| 通信 | 必要な前提 |
| --- | --- |
| publisher / worker から controller | 同じ Bearer token を設定する。controller が TLS を終端する場合は証明書を検証できること |
| controller の peer 間 | 固有 URL へ相互に接続でき、全 peer が信頼できること |
| client から controller | マスターとメディアプレイリストに接続でき、follower の `307` に追従できること |
| client から worker | プレイリストに書かれた公開 URL へ接続できること |
| client から鍵配信元 | 鍵 URI へ接続でき、必要な認証と cookie を送れること |

controller の GET と sync には認証がない。
読み取りを公開しても内部の同期や登録を無条件に公開してよいわけではないため、プライベートネットワーク、ファイアウォール、API ごとのアクセス制御などで制限する。
CORS はブラウザの読み取り許可であり、API へのアクセス制御や認証の代わりにはならない。

controller は HTTP または TLS で待ち受ける。
TLS を使わずに信頼できないネットワークへ公開する場合は、前段で TLS 終端を用意する。
controller または worker 自身で終端する場合は [controller の TLS 配信](./controller.md#tls-配信) と [worker の TLS / ACME](./worker.md) を参照する。
ブラウザのページが HTTPS の場合は、プレイリスト、セグメント、鍵も HTTPS で取得できるようにし、mixed content を避ける。

ブラウザの再生では controller、worker、鍵配信元のすべてに適切な読み取り用 CORS が必要になる。
セッション cookie を使う鍵配信元では、プレイヤーの credentials 設定、許可 origin、cookie の SameSite / Secure 属性も確認する。
Edamame の `--cors-origin` は GET 用であり、PUT / POST のブラウザからの呼び出しや credentials 付き CORS を設定するものではない。

外部配信への判定は TCP 接続元 IP に依存し、転送ヘッダーから視聴者の IP を復元しない。
NAT やプロキシを使う場合は、視聴者単位の割合にならないことを考慮する（[外部配信](./controller.md#外部配信への振り分け)）。

## 起動と通信を確認する

controller と worker の起動順序は問わないが、確認時は [導入手順](../README.md#最短での起動手順) の順にすると切り分けやすい。
次の順で確認する。

1. `/health` が応答することと、`/internal/cluster/health` で leader が確定していることを確認する。
2. worker の登録と sync のログを確認する。
3. セグメントを PUT し、返された `sequence` を確認する。
4. 公開待ちと取得完了後に master と全 quality のメディアプレイリストを取得する。
5. メディアプレイリストにある実際の URL からセグメントを取得する。

[導入手順のダミーデータ](../README.md#動作を確認する) は保存と配信経路だけを確認するためのもので、MPEG-TS ではなく再生には使えない。
再生確認では実際の映像を使い、同じ channel / quality にビットレートやセグメント長の違う素材を混ぜない。
初回 PUT 前の `404`、公開範囲が決まるまでの `503` と、公開後の失敗を区別する。

## 再生を確認する

非暗号化の検証には [検証用 publisher](./publisher.md#検証用-publisher) を使える。
付属のライブ publisher は常に暗号化するため、[publisher の起動条件](./publisher.md) に従って鍵配信も用意する。
client に `{controller_url}/channels/{channel_id}/master.m3u8` を設定し、次を確認する。

- master に必要な全 quality があり、それぞれのプレイリストを取得できる
- セグメントの実際の URL へ client と同じネットワークからアクセスできる
- 暗号化する場合は `#EXT-X-KEY` の URI と IV が正しく、対象セグメントの鍵を取得できる
- 鍵配信にセッションが必要なら、実プレイヤーと同じ cookie / credentials で取得できる
- 実プレイヤーで映像と音声が再生され、想定した解像度になり、再生時刻が継続して進む
- 画質を切り替えても再生でき、worker の停止と controller 交代後の復旧も許容できる

HTTP の成功、ffprobe による解析、手動復号の成功だけで再生可能とは判断しない。
同じ鍵 URI の中身を入れ替えるとプレイヤーの鍵キャッシュが残る場合があるため、publisher の再起動と鍵の寿命も含めて確認する。

## 障害を切り分ける

| 症状 | 最初に確認すること |
| --- | --- |
| プロセスへ接続できない | `--bind`、公開ポート、DNS、TLS、プロキシの転送先。`/health` の応答だけでは配信可能とは判断しない |
| プレイリストが `404` | channel / quality へ PUT 済みか、再起動または leader 交代で状態が失われていないか |
| PUT が `401` | publisher / worker / 全 controller の token が一致しているか |
| PUT が `409` | 同じ識別子のバイト列、duration、bandwidth、resolution の固定条件を破っていないか |
| PUT が `413` | 1 セグメントが保存容量または 64 MiB の HTTP 上限を超えていないか |
| プレイリストが `503` | leader、公開待ち、publisher の停止、worker の登録と sync、公開範囲全体のキャッシュ有無。詳細は [controller](./controller.md#公開範囲の決定) |
| プレイリストが `422` | 公開範囲の原本が容量超過で消えていないか。容量と入力の最大サイズを見直す |
| worker のセグメントが `404` | プレイリストが古くないか、worker の再起動や再登録でキャッシュを捨てていないか。worker はリクエスト時に原本を取得しない |
| worker が登録されない | token、`--controller-url`、ネットワークの疎通。controller が TLS を終端する場合は証明書を検証できるか。ACME の場合は公開ルート CA で有効な証明書を取得できているか |
| 同期は成功するが公開が遅れる | バッチの直列取得が詰まっていないか、cache-limit が小さすぎないか、公開待ちが取得に足りるか |
| 最後の映像から進まない | publisher の入力と PUT、新規保存からの経過時間を確認する。猶予を超えるとその quality は停止中になり、メディアプレイリストは `503`、マスタープレイリストからは除外される。再開しても停止前のセグメントは公開されない |
| 解像度や音声が設定と違う入力を送った | publisher の拒否ログを確認し、送信側の設定を直して再接続する。拒否では channel は止まらず、ffmpeg を起動し直して次の入力を待つ |
| controller を再起動した | 状態と採番は失われる。worker は再登録後にキャッシュを捨て、publisher は新しいセグメントを送る必要がある |
| leader が交代した | 状態の復元は行わない。外部配信の再登録とプレイヤーの再開が必要な場合がある。[冗長化の制約](./cluster.md#交代時の状態と復旧) を確認する |
| DNS が停止機体を返す | 停止機体の A レコードを除き、接続失敗を再試行する。短い TTL だけで即時切り替えは保証できない |
| HTTP は成功するが復号できない | 対象セグメントの鍵、IV、URI、鍵の入れ替え、cookie と CORS を確認する |
| 外部配信へ転送後に失敗する | controller は外部の状態を監視しない。登録先を確認し、停止するなら外部配信登録を解除する |

ログは英語で出力する。
登録、sync、セグメント取得の失敗は各プロセスのログと [メトリクス](./observability.md) を合わせて確認する。
